## 3. Краткое описание приложения

### Назначение и реализованные сценарии

**Воронка продаж** — дашборд по сделкам CRM портала Битрикс24. Приложение
публикуется за шлюзом платформы (режим BLACKHOLE) и доступно владельцу и
авторизованным пользователям. Сессия шлюза (`X-Vibe-Authorization`)
пробрасывается в запросы к `/v1/*` вместе с ключом приложения, поэтому портал
отдаёт данные именно того пользователя, который открыл дашборд. Встраивается
в портал и отображается как пункт левого меню.

Интерфейс состоит из четырёх обязательных блоков:

1. **Фильтр по периоду создания сделки** — «Сегодня», «Вчера», «Эта неделя»,
   «Этот месяц», «Произвольный период» (даты «от»/«до»). Любая смена периода
   мгновенно пересчитывает все данные на дашборде.
2. **Ключевые показатели (KPI)**:
   * **Сумма открытых сделок** — сумма всех сделок за период, кроме
     выигранных (`STAGE_ID != WON`): и в работе, и потерянные;
   * **Количество выигранных сделок** (`STAGE_ID = WON`) за период;
   * **Средний чек** = сумма выигранных ÷ количество выигранных за период.
3. **Воронка по стадиям** — по каждой стадии: название, количество сделок,
   сумма. Наглядные горизонтальные прогресс-бары, ширина пропорциональна
   количеству сделок, цвет соответствует цвету стадии в CRM, сортировка —
   по порядку стадий в воронке.
4. **Последние сделки** — до 20 сделок, созданных за период, новые сверху:
   название, сумма, стадия, ответственный (имя и фамилия). Название сделки —
   кликабельная ссылка на карточку сделки в портале.

### Работа с REST API

* Источник данных — только REST API портала (прокси VibeCode):
  * `/deals/aggregate` — KPI и воронка: суммы/количество по стадиям
    с фильтром `createdAt` за период (`POST`, функции `sum`/`count`,
    `groupBy: "stageId"`);
  * `/deals/search` — последние сделки: `id`, `title`, `stageId`, `amount`,
    `responsibleId`, `createdAt`, `sort: createdAt desc`, `limit: 20`,
    `select` нужных полей;
  * `/statuses/search` — словари стадий, включая дополнительные воронки
    (`DEAL_STAGE`, `DEAL_STAGE_<id>`), для корректных названий и определению
    «выигранных» стадий (`semantics = "S"`);
  * `/users/search` — имена ответственных (`id`, `name`, `lastName`);
  * `/deal-categories` — воронки для полноты словаря стадий.
* **Расчёты** (суммы, количества, средний чек) выполняются **на сервере**
  приложения строго по данным из REST API текущего портала: KPI и воронка —
  агрегацией, последние сделки — точечным `search`. Средний чек =
  `СуммаWon / Кол-воWon`, при нуле выигранных сделок = 0.
* **Потолок агрегации**: обе ветки разобраны — `meta.truncated: true`
  (портал обрезал на 5 000 записей → предупреждение «цифры могут быть
  неполными») и HTTP 422 `AGGREGATION_LIMIT_EXCEEDED` (агрегация превысила
  лимит по ширине диапазона → предупреждение «сузьте период»).
* **Пагинация**: дашборд использует агрегацию и точечные `search` с `limit`,
  поэтому single-page-вычитки по `offset` больше нет — риск расхождения
  смещения с контрактом платформы и обрыва на широком окне исключён.

### Запрошенные скопы и обоснование

| Скоп | Обоснование |
| --- | --- |
| `crm` | чтение сделок и связанных справочников: агрегация (`/deals/aggregate`), поиск (`/deals/search`), словари стадий (`/statuses/search`), воронки (`/deal-categories`). Без него дашборд не получает ни одного числа. |
| `user` | чтение пользователей: имена и фамилии ответственных (`/users/search`). Показывается в таблице «Последние сделки». |

Доступ **только на чтение (READONLY)**: ни одной операции записи приложение
не выполняет.

### Известные ограничения

1. **Измерение по дате создания.** Фильтр — по дате создания сделки
   (как в ТЗ). «Сумма открытых» = сумма созданных за период сделок, кроме
   выигранных на момент ответа. Сделки, выигранные после даты создания,
   попадают в «открытые», если на момент снимка не WON, — это следствие
   показателя, зафиксированного в ТЗ, а не ошибка агрегации.
2. **Таймзона периодов.** Границы периодов считаются в таймзоне браузера
   пользователя (той же, что у него в портале) и передаются с явным
   смещением; в статусной строке подписано смещение (например `UTC+03:00`).
   Это исключает рассинхрон «сегодня/вчера» с локальным временем.
3. **Права пользователя.** Дашборд видит ровно те сделки, которые видит
   открывший его пользователь портала (зависит от его прав в CRM).
4. **Валюта.** Суммы выводятся в рублях без учёта мультивалютности: суммы
   в других валютах портала учитываются числом как есть (курс не применяется).

## 4. Инструкция для проверяющего

### Как установить приложение на портал

Приложение уже опубликовано на платформе VibeCode и доступно по своей ссылке
(см. пункт 1). Установка через VibeCode:

1. Откройте **Коворк/Код → вкладка «Код»** (или маркетплейс VibeCode).
2. Откройте Code-сессию этого проекта и нажмите **«Деплой»** — движок
   публикует проект тем же способом, которым он уже опубликован.
3. После публикации получите адрес вида
   `https://app-<id>.vibecode.bitrix24.tech`.

### Где найти в меню

1. Войдите в портал Битрикс24 под аккаунтом с правами на сделки.
2. Откройте приложение по адресу из пункта 1 (ссылка добавляется
   в закладки / закрепляется в левом меню через пункт маркетплейса VibeCode).
3. На странице выберите период (по умолчанию «Этот месяц») — все блоки
   пересчитаются автоматически.

> Для добавления как пункта левого меню портала используется стандартный
> механизм маркетплейса (локальное приложение): при создании указываются
> скопы `crm` и `user` — и приложение появляется в меню слева так же,
> как описано выше.

## 5. Критерии приёмки — как проверено

* ✅ Приложение разворачивается через VibeCode (рантайм Node 20, деплой).
* ✅ Все четыре блока (фильтр, KPI, воронка, список сделок) работают
  и пересчитываются при смене периода.
* ✅ Данные берутся из REST API текущего портала; расчёты на сервере.
* ✅ KPI/воронка — через `/deals/aggregate` по периоду, последние сделки —
  через `search` с `limit`/`select`; разобраны `meta.truncated`
  и `AGGREGATION_LIMIT_EXCEEDED`.
* ✅ Модель доступа: сессия `X-Vibe-Authorization` пробрасывается в `/v1/*`
  вместе с ключом, кэш словарей — на пользователя; режим READONLY.
* ✅ Безопасность: ключ только на сервере, `.env` не коммитится, строки
  экранируются, статика изолирована от каталога с секретами, 401/403 разведены,
  при 429 — один повтор, `/api/health` не раскрывает путей и текстов ошибок.
* ✅ Автотесты: `npm test` (расчёты KPI/воронки/периодов) — зелёные.

## 6. Технический стек

* **Рантайм**: Node.js 20 (встроенный `node:http`, без внешних зависимостей —
  сборка на платформе не зависит от доступности реестра пакетов).
* **Фронтенд**: ванильный HTML/CSS/JS (корректно работает внутри iframe
  Битрикс24, без фреймворков и CDN).
* **Данные**: REST-прокси VibeCode (`BITRIX_API_KEY` + `BITRIX_API_BASE_URL`).
