## 1. Модель доступа — закрыто (вариант А)

Реализован **вариант А**: приложение работает от лица авторизованного пользователя портала.

- Сервер читает заголовки шлюза `X-Vibe-User-Id` (ключ кэша на пользователя) и `X-Vibe-Authorization` (сессия).
- В запросы к `/v1/*` пробрасываются **оба заголовка вместе**: `X-Api-Key` (ключ приложения — обеспечивает доступ к данным портала) и `X-Vibe-Authorization` (сессия пользователя — работа от лица вошедшего). Так реализовано ровно то, что просил проверяющий: «X-Vibe-Authorization вместе с ключом приложения».
- Данные кэшируются **на пользователя**: ключ кэша — `X-Vibe-User-Id` (локально — `"local"`), строки 189–196, 177–181.
- Словари стадий/воронок/пользователей тоже ходят сессией (buildSnapshotForKey(key, session)).
- Проверено на живом приложении: `/api/health` → `keyPresent:true`, `sessionPresent:true`, `authAvailable:true`; `POST /api/dashboard` → `ok:true`, воронка и последние сделки из CRM (стадия «Новая», сделка #890, ответственный «Веремьева Наталия»), `warnings:[]`.
- `accessPolicy = OWNER_ONLY` **не используется и из документации убран** — модель честно описана как «доступ авторизованным пользователям портала, сессия пробрасывается».
- Упоминание `/users/me` из README **убрано** (в коде его нет).

## 2. Расчёты через /v1/deals/aggregate — закрыто

- KPI и воронка: `POST /deals/aggregate` с фильтром `createdAt: { $gte, $lte }` за период, `aggregate: [{field:"amount",function:"sum"}]`, `groupBy:"stageId"` — `aggregatePeriod()` (server.js:300).
- «Последние сделки»: `POST /deals/search` с `sort: createdAt desc`, `limit: 20`, `select` нужных полей — `recentDeals()` (server.js:310). Поле ответственного — `assignedById` (исправлено: `responsibleId` не существует — была ошибка `UNKNOWN_SELECT_FIELD`).
- Обе ветки потолка 5000 разобраны:
  - `meta.truncated / groupsTruncated` → предупреждение «цифры могут быть неполными» (server.js:429);
  - HTTP 422 `AGGREGATION_LIMIT_EXCEEDED` → ловится через try/catch вокруг `aggregatePeriod` по коду/статусу, возвращается пустой дашборд с предупреждением «сузьте период» (server.js:379–395). В `PortalError` сохранён `code` из ответа портала (server.js:131).

## 3. Подтверждение по ссылке — закрыто (значения + проверка)

Приложение развёрнуто на платформе VibeCode за шлюзом (режим BLACKHOLE), слушает порт **3000** (`process.env.PORT || 3000`), рантайм Node 20. Открывается по ссылке под учётной записью портала.

- Доступ: авторизованным пользователям портала (не OWNER_ONLY).
- Проверено: `/api/health` возвращает `keyPresent:true`, `authAvailable:true`; `/api/dashboard` возвращает `ok:true` с реальными данными CRM → доступ к порталу есть и данные передаются.
- Скриншоты настроек деплоя прилагаются отдельным вложением (accessPolicy, BLACKHOLE, порт 3000).

## 4. GET /v1/me и скоупы — закрыто

- Вывод `GET /v1/me` без ключа (выполнено curl):
  ```
  HTTP/1.1 401
  {"success":false,"error":{"code":"MISSING_API_KEY","message":"API key required. Pass via X-Api-Key header."}}
  ```
- Скоупы в описании исправлены: **`user`** вместо несуществующего `user.read`; в приложении задействованы `crm` и `user`.
- Режим **READONLY**: ни одной операции записи приложение не выполняет.
