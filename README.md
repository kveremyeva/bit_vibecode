# Воронка продаж — дашборд Битрикс24 (VibeCode)


## Назначение

Приложение показывает аналитику по сделкам CRM текущего портала Битрикс24:

* **Блок фильтрации** — период создания сделок: «Сегодня», «Вчера»,
  «Эта неделя», «Этот месяц», «Произвольный период» (даты «от» и «до»).
  Смена периода мгновенно пересчитывает все блоки.
* **Ключевые показатели (KPI)**:
  * общая сумма **открытых** сделок (`STAGE_ID != WON`, т.е. все, кроме
    выигранных, в терминологии ТЗ);
  * количество выигранных сделок (`STAGE_ID = WON`) за период;
  * средний чек = сумма выигранных / количество выигранных за период.
* **Воронка по стадиям** — по каждой стадии количество сделок и сумма;
  наглядные горизонтальные прогресс-бары, отсортированные по воронке.
* **Последние сделки** — до 20 последних по дате создания (новые сверху):
  название, сумма, стадия, ответственный (имя и фамилия).

Расчёты выполняются **на сервере**. KPI и воронка считаются агрегацией
портала `/deals/aggregate` с фильтром по дате создания за период, список
последних сделок — отдельным `search` с `limit` и `select`. Ключ портала
хранится только в окружении сервера и в браузер не попадает.

## Архитектура

```
┌─────────────┐   /api/dashboard   ┌──────────────────────────┐
│  Браузер    │ ─────────────────► │  Node-сервер (server.js) │
│  (iframe    │                     │  фоновый снапшот         │
│  Битрикс24) │ ◄───────────────── │  сделки/стадии/пользователи
└─────────────┘   JSON + статика   └────────────┬─────────────┘
                                                │ REST-прокси
                                                ▼
                                       Битрикс24 (REST API)
```

* **server.js** — встроенный `node:http`, без внешних зависимостей. Хранит кэш
  данных **на пользователя** (по `X-Vibe-User-Id`), пробрасывает сессию шлюза
  `X-Vibe-Authorization` в портальные запросы вместе с ключом приложения и
  отдаёт `/api/dashboard`, `/api/health`, `/api/meta` и статику из `public/`.
* **lib/calc.js** — чистые функции расчётов (KPI, воронка, последние сделки,
  периоды) + юнит-тесты (`node --test`).
* **public/** — статический интерфейс: `index.html`, `styles.css`, `app.js`.
  Никаких внешних пакетов и CDN-библиотек (шрифты — системные).

## Скопы (права) приложения

| Скоп | Зачем |
| --- | --- |
| `crm` | чтение сделок: агрегация и поиск (`/deals/aggregate`, `/deals/search`), словари стадий (`/statuses/search`), воронки (`/deal-categories`) |
| `user` | данные ответственных — имя и фамилия (`/users/search`) |

Доступ к прокси уже настроен: `BITRIX_API_KEY`, `BITRIX_API_BASE_URL`,
`BITRIX_PORTAL_DOMAIN` приходят в окружение приложения (локально из `.env`,
на сервере из переменных окружения деплоя). Ключ в коде не хардкодится и не
коммитится. Доступ — **только на чтение** (READONLY): ни одной операции
записи приложение не выполняет.

## Модель доступа

Приложение публикуется за шлюзом платформы и доступно **владельцу** и
авторизованным пользователям. В каждый запрос шлюз добавляет заголовки
`X-Vibe-User-Id`, `X-Vibe-Authorization`, `X-Vibe-User-Role`. Сервер читает их
и **пробрасывает сессию** (вместе с ключом приложения) в запросы к `/v1/*` —
портал отдаёт данные именно того пользователя, который открыл дашборд.
Снимок словарей кэшируется **на пользователя** (по `X-Vibe-User-Id`, локально
— `local`), а KPI/воронка пересчитываются агрегацией на лету по периоду.

Локально (без шлюза) `X-Vibe-*` отсутствуют — сервер работает по ключу
приложения напрямую, что равносильно сервисному режиму владельца.

## Локальный запуск

```bash
npm install     # без зависимостей — мгновенно
npm start       # server.js на http://localhost:3000
npm test        # юнит-тесты расчётов
```

Если рядом с проектом лежит `.env` (или в окружении заданы переменные) —
приложение сразу обратится к порталу. Без ключа сервер всё равно стартует,
а `/api/dashboard` честно сообщает «портал не подключён» (код `no_key`,
HTTP 503) — приложение остаётся развёртываемым, ключ можно подключить позже.

## Периоды — важная деталь логики

В ТЗ указано «фильтр по периоду **создания** сделки». Поэтому:

* фильтр `DATE_CREATE` применяется ко **всем** блокам;
* «Открытые» = все созданные за период, **кроме выигранных** (по ТЗ:
  `STAGE_ID != WON` — в эту сумму входят и находящиеся в работе, и потерянные);
* «Выигранные» — созданные за период и имеющие стадию с семантикой WON
  (`semantics = "S"` в словаре стадий; для классической воронки это код `WON`);
* разница «сумма открытых» vs «сумма выигранных» связана со стадией на момент
  снимка: сделка могла быть выиграна позже даты создания.

## Агрегация и потолок 5000

KPI и воронка считаются сервером портала через `POST /deals/aggregate`
с фильтром `createdAt` за период и группировкой по стадии. Список последних
сделок — `POST /deals/search` с `sort: createdAt desc`, `limit: 20` и `select`
нужных полей. Обе ветки потолка агрегации разобраны:

* `meta.truncated: true` — портал обрезал расчёт на 5 000 записей: в ответе
  появляется предупреждение «цифры могут быть неполными»;
* `error.code == "AGGREGATION_LIMIT_EXCEEDED"` (HTTP 422) — агрегация превысила
  лимит по ширине диапазона: показывается предупреждение «сузьте период».

Пагинация single-page-вычитки сделок больше не нужна: всё считается
агрегацией и точечным `search`.

## Периоды и таймзона

Границы периодов («Сегодня», «Вчера», «Эта неделя», «Этот месяц»,
«Произвольный») вычисляются **в таймзоне браузера пользователя** (той же,
что у него в портале), а не в UTC сервера. Конкретные `from`/`to` с явным
смещением передаются в API, и агрегация идёт ровно по локальной дате. Для
«произвольного периода» дата «до» приводится к последней миллисекунде дня
(сделки, созданные в этот день позже полуночи, не теряются). На экране в
строке статуса подписано смещение (`UTC+03:00` и т.п.).

## Безопасность

* Ключ портала — только на сервере (`process.env`, заголовок `X-Api-Key`),
  фронтенд ходит только на свои `/api/*`.
* `.env` в `.gitignore` и исключается из архива деплоя; в коде нет секретов.
* Все строки из портала экранируются при выводе в HTML (`escapeHtml`).
* Встроенный сервер отдаёт статику только из `public/` (защита от
  path traversal и от отдачи `.env`).
* Классификация ошибок портала по типам (`no_key`, `timeout`, `rate_limited`,
  `denied`, `forbidden`, `portal_error`). `401` (сессия/ключ) и `403` (не хватает
  прав на сделки) разведены в разные сообщения — ключ упоминается только там,
  где проблема действительно в нём.
* Словарь стадий не «проглатывается»: если `/statuses/search` не собрался,
  в статусной строке появляется явное предупреждение (а не тихая подмена
  логики определения «выигранных»).
* При `429` сервер повторяет запрос один раз, уважая `Retry-After`.
* `/api/health` не раскрывает путей и текстов ошибок — только факт наличия
  ключа (`keyPresent`).
