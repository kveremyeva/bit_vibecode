# Воронка продаж — дашборд Битрикс24 (VibeCode)


## Назначение

Приложение показывает аналитику по сделкам CRM текущего портала Битрикс24:

* **Блок фильтрации** — период создания сделок: «Сегодня», «Вчера»,
  «Эта неделя», «Этот месяц», «Произвольный период» (даты «от» и «до»).
  Смена периода мгновенно пересчитывает все блоки.
* **Ключевые показатели (KPI)**:
  * общая сумма **открытых** сделок (`STAGE_ID != WON`, т.е. все, кроме
    выигранных, в терминологии ТЗ);
  * количество выигранных сделок (`STAGE_ID = WON`) за период;
  * средний чек = сумма выигранных / количество выигранных за период.
* **Воронка по стадиям** — по каждой стадии количество сделок и сумма;
  наглядные горизонтальные прогресс-бары, отсортированные по воронке.
* **Последние сделки** — до 20 последних по дате создания (новые сверху):
  название, сумма, стадия, ответственный (имя и фамилия).

Расчёты выполняются **на сервере** на основе данных REST API портала
(`crm.deal.list`-эквивалент — поиск сделок, словарь стадий, пользователи).
Ключ портала хранится только в окружении сервера и в браузер не попадает.

## Архитектура

```
┌─────────────┐   /api/dashboard   ┌──────────────────────────┐
│  Браузер    │ ─────────────────► │  Node-сервер (server.js) │
│  (iframe    │                     │  фоновый снапшот         │
│  Битрикс24) │ ◄───────────────── │  сделки/стадии/пользователи
└─────────────┘   JSON + статика   └────────────┬─────────────┘
                                                │ REST-прокси
                                                ▼
                                       Битрикс24 (REST API)
```

* **server.js** — встроенный `node:http`, без внешних зависимостей. Собирает
  снимок данных в фоне (портал отвечает десятками секунд — запрос посетителя
  никогда не ждёт портал), обслуживает фронтенд из памяти и отдаёт
  `/api/dashboard`, `/api/health`, `/api/meta` и статику из `public/`.
* **lib/calc.js** — чистые функции расчётов (KPI, воронка, последние сделки,
  периоды) + юнит-тесты (`node --test`).
* **public/** — статический интерфейс: `index.html`, `styles.css`, `app.js`.
  Никаких внешних пакетов и CDN-библиотек.

## Скопы (права) приложения

| Скоп | Зачем |
| --- | --- |
| `crm` | чтение сделок: поиск, суммы, стадии (`/deals/search`), словари стадий (`/statuses/search`), воронки (`/deal-categories`) |
| `user.read` / `user` | данные ответственных — имя и фамилия (`/users/search`), текущий пользователь (`/users/me`) |

Доступ к прокси уже настроен: `BITRIX_API_KEY`, `BITRIX_API_BASE_URL`,
`BITRIX_PORTAL_DOMAIN` приходят в окружение приложения (локально из `.env`,
на сервере из переменных окружения деплоя). Ключ в коде не хардкодится и не
коммитится.

## Локальный запуск

```bash
npm install     # без зависимостей — мгновенно
npm start       # server.js на http://localhost:3000
npm test        # юнит-тесты расчётов
```

Если рядом с проектом лежит `.env` (или в окружении заданы переменные) —
приложение сразу обратится к порталу. Без ключа сервер всё равно стартует,
а `/api/dashboard` честно сообщает «портал не подключён» (код `no_key`,
HTTP 503) — приложение остаётся развёртываемым, ключ можно подключить позже.

## Периоды — важная деталь логики

В ТЗ указано «фильтр по периоду **создания** сделки». Поэтому:

* фильтр `DATE_CREATE` применяется ко **всем** блокам;
* «Открытые» = все созданные за период, **кроме выигранных** (по ТЗ:
  `STAGE_ID != WON` — в эту сумму входят и находящиеся в работе, и потерянные);
* «Выигранные» — созданные за период и имеющие стадию с семантикой WON
  (`semantics = "S"` в словаре стадий; для классической воронки это код `WON`);
* разница «сумма открытых» vs «сумма выигранных» связана со стадией на момент
  снимка: сделка могла быть выиграна позже даты создания.

## Пагинация

Снимок собирается постранично через `offset/limit` до полного вычитка
(до 5 000 сделок за запрос — прокси сам дочитывает встроенные 50-страницы
портала). `meta.hasMore` закрывает цикл; пустого «обрезанного» дашборда быть
не может — считается весь снимок, а не одна страница.

## Безопасность

* Ключ портала — только на сервере (`process.env`, заголовок `X-Api-Key`),
  фронтенд ходит только на свои `/api/*`.
* `.env` в `.gitignore` и исключается из архива деплоя; в коде нет секретов.
* Все строки из портала экранируются при выводе в HTML (`escapeHtml`).
* Встроенный сервер отдаёт статику только из `public/` (защита от
  path traversal и от отдачи `.env`).
* Классификация ошибок портала по типам (`no_key`, `timeout`, `rate_limited`,
  `denied`, `portal_error`) с честными текстами — ключ упоминается только там,
  где проблема действительно в нём.
